```

[변경 후]
| execution_date | str | 불가 | ISO 8601 날짜 (**미국 거래일 ET 기준**, 예: "2026-04-10").
  GitHub Actions runner 가 `TZ=America/New_York` 에서 `date.today()` 를 사용하므로,
  cron 실행 시각이 한국 시간 기준 다음 날이어도 필드 값은 실행일 기준 미국 거래일로 저장된다. |
```

### 앱 점검 포인트

  - **옵션 2 (현상 유지)**: 코드 근처에 "ET 기준 `execution_date` 와 KST `today()` 사이에 1일 오프셋 존재. `STALE_WARNING_DAYS=4` 가 이를 흡수한다" 주석 추가

## 7. §8.3 `processed` 필드 규칙 문단 뒤 두 문단 신규 추가

### 추가된 내용

**(1) 마킹 후 잔존**:
> 처리 완료 (`processed=true`) 마킹된 inbox 레코드는 RTDB 에서 **삭제되지 않고 잔존**한다. `/history/*` 는 별도 미러이며 inbox 레코드가 이동하는 구조가 아니다. 현재 rolling 정리 로직이 없으므로 운영상 누적된다 (Spark 플랜 + 연간 수천 건 규모까지 허용). 전체 초기화는 `reset` 명령이 네 inbox 경로를 통째 삭제한다.

**(2) 실패 처리 계약**:
> 실패 시 자동 DLQ / 재시도 큐 / per-UUID 결과 채널은 없다. 다음 cron 실행 또는 `workflow_dispatch` 수동 재실행이 재시도를 담당하며, `applied_*_ids.json` 원장과 RTDB `set()` 덮어쓰기가 중복 반영을 방지한다. 반영 실패는 전체 `run-daily` 실패와 동일하게 FCM + 텔레그램 실패 알림 (§6.3) 으로만 전달된다.

### 변경 이유
감사 §1.1 / §1.2 에서 앱이 "처리된 inbox 가 /history 로 이동" 또는 "per-UUID 결과 채널이 있다" 고 가정할 위험이 확인됨. 실제 동작을 설계서에 명시.

### 앱 점검 포인트

- [ ] `rtdb.ts` 의 `readInbox` 등에서 `processed !== true` 필터가 유지되고 있는지 확인 (inbox 가 계속 쌓이므로 이 필터가 필수)
- [ ] 체결/보정 입력 후 UX 안내 문구 점검 — "결과는 익일 장마감 후 푸시 알림으로 확인하세요" 또는 동등한 안내가 있는지
- [ ] per-UUID 실패 확인을 기다리는 대기 UI 가 있다면, 현재 계약상 제공되지 않음을 반영하여 "성공 토스트 후 익일 결과 대기" 로 단순화 (선택)

## 8. §11 보안 섹션 권한 표 신규 추가

### 추가된 내용
§11 기존 첫 문단과 GitHub 토큰 설명 사이에 다음 표 + 3개 bullet 삽입:

> 각 RTDB 경로의 접근 권한 설계 (Firebase Console Rules 에 반영):
>
> | 경로 | 읽기 | 쓰기 |
> |---|---|---|
> | `/latest/*`, `/charts/*`, `/history/*` | `auth.uid === OWNER_UID` | 쓰기 금지 (Admin SDK 는 Rules 우회) |
> | `/fills/inbox/*`, `/balance_adjust/inbox/*`, `/fill_dismiss/inbox/*`, `/model_sync/inbox/*` | `auth.uid === OWNER_UID` | `auth.uid === OWNER_UID` |
> | `/device_tokens/{device_id}` | `auth.uid === OWNER_UID` | `auth.uid === OWNER_UID` |
>
> - Admin SDK 는 Rules 를 우회. 서버 daily runner 의 모든 쓰기는 Rules 와 무관하게 성공한다.
> - 앱은 Firebase Auth Email/Password 로 로그인한 OWNER_UID 계정으로만 접근한다.
> - `/device_tokens/{device_id}` 의 "타 사용자 deviceId 덮어쓰기" 리스크는 OWNER_UID 단일 계정 전제하에서 자연 차단된다.

### 변경 이유
감사 §2.3 에서 설계서의 Rules 스펙이 한 문장뿐이라는 지적이 있었음. 사용자가 Firebase Console 에서 실제 Rules 가 본 표와 일치함을 확인 완료한 상태이며, 이를 설계서에 문서화.

### 앱 점검 포인트

- [ ] 앱이 쓰려 하는 경로가 위 표의 "쓰기 허용 경로" 안에 있는지 재확인
- [ ] 권한 거부(Permission Denied) 에러 처리 경로가 있는지, 있으면 사용자에게 보여주는 메시지가 명확한지 점검 (예: "RTDB 접근 권한이 없습니다. 로그인 상태를 확인해 주세요")
- [ ] `OWNER_UID` 상수가 앱에 하드코딩되어 있다면 src/live/CLAUDE.md 의 값과 일치하는지 재확인
